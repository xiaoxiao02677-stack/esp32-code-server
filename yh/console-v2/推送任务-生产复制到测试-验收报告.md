## 二、架构认知（关键，与订单模块不同）

**推送任务不在 Java 侧**。两边 `manager-api` 都无 push 模块、数据库也无 push 表。真实链路是：

```
前端 /yuhe/api/push/*
   → nginx → Java manager-api(8002) PythonApiProxyController（用用户 token 鉴权，换成 server.secret）
   → Python yuhe-server(8003) core/api/push_handler.py
   → core/services/push_scheduler.py + topic_generator.py
```

Python 侧涉及 3 个文件：`core/api/push_handler.py`、`core/services/push_scheduler.py`、`core/services/topic_generator.py`。

`config/config_loader.py` 在从 API 读取配置时，把 `server` 段**硬编码为 7 个字段**（`ip/port/http_port/vision_explain/auth_key/heartbeat_port/auth`），`public_audio_base_url` 会被丢弃。而 `topic_generator` 推导音频 base 时优先取 `public_audio_base_url`，缺失时回退从 `vision_explain` 推导——所以唯一生效的抓手是 `vision_explain`。

## 六、已知限制与后续建议

1. **测试环境无在线设备**：`pushOnlineDevices` 返回空数组。端到端投递（TTS→转码→设备播放）需在测试环境接入真实设备后才能完整验证。我用脚本直接调用 `generate_for_agent` 会因缺少真实连接上下文（`wake_word_service=None`、无在线 conn）走 manager-api 反查路径并报 `asyncio.run 嵌套`，这是**验证脚本的局限**，不是迁移缺陷（生产同样脚本也复现同样报错，但生产真实链路正常）。
2. **音频 URL 端口**：测试已统一走 8103；若后续测试环境 8003 直接对外，可改回与生产一致的形态。
3. **`_resolve_tts_config` 在 async 上下文调同步 API** 会触发 `asyncio.run 嵌套`。生产在有在线设备时不走该路径，属于潜在健壮性问题，建议后续把该调用改为 async（两边同步修改以保持 1:1）。
4. **测试库 token 需定期续期**：`sys_user_token` 中 demo 的 token 会过期，导致接口 401；生产因持续有请求会自动续期。
