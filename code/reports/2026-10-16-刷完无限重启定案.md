# 刷完无限重启定案：「4MB 布局的 app + 16MB 布局的分区表」

- 日期：2026-10-16
- 设备：COM18（USB-SERIAL CH340K）
- 现象：刷完屏幕全程不亮；串口里 `bootloader_reset at bootloader_utility.c:1163` +
  `rst:0x3 (RTC_SW_SYS_RST)` 无限循环
- 结论：**不是固件问题，是设备里的内容与分区表不同源**。这一轮 `build.py` /
  `flash.py` 编出来的 `yh-154tft-wifi` 产物本身没有问题。

## 1. 取证方式（全部只读，不写设备）

`hardware/sets/diag.py` 只读回读关键区域，再逐段与 `<FW>/build/*.bin` 比对；
配合按 4KB/64KB 分块在本地文件里定位同源内容。原始回读数据留在
`.trash/dev_dump/`（`dev_0x00000_64k.bin`、`dev_0x20000_256k.bin`、`0x10000_64k.bin`、
`0x60000_128k.bin`、`0xf000_phy.bin`）。

## 2. 设备实况

| 区域 | 设备上是什么 | 判据 |
|---|---|---|
| `0x0` bootloader | 入口 `0x403c88f4`、16736 字节 | 与 `hardware/big_secreen/xiaozhi-esp32/build/bootloader/bootloader.bin` **只差 36 字节**；**不是**本次 sets 编的（`0x403c88dc`、15536 字节） |
| `0x8000` 分区表 | **16MB 布局**：nvs 0x9000 / otadata 0xd000 / phy_init 0xf000 / **ota_0 0x20000** / ota_1 0x410000 / assets 0x800000 | 与 `build/build/partition_table/partition-table.bin` 逐字节一致（3072 字节）。注：三套工程（sets / big_secreen / small_screen_camera）这张表**完全相同**，所以它不能反证「是本次烧的」 |
| `0xd000` otadata | `01 00 00 00 …`（合法的 ota_0 记录） | 本地产物 `ota_data_initial.bin` 是**全 0xFF** —— 这条是设备早期运行时自己写的 |
| **`0x10000`** | **一份完整合法 app 镜像**：`e9 06 02 4f`、entry `0x403799c0`、6 段、seg0 len `0x0a81b8` | `esp_app_desc` = **version 2.5.3 / Oct 16 2026 22:13:45 / idf v6.1-dirty**。**全仓找不到任何 2.5.3 产物，git 历史里也从未出现过** |
| `0x20000`（ota_0） | **不是镜像头**：首字节 `0x67` = 字符 `g` | 该处是一段字符串（`generation(snprintf of subprotocol returned %d, …`），正是 `0x10000` 那份 app 的**内部 rodata**（文件偏移 `0x10000`）—— 即那份 2.7MB 的 app 是以 0x10000 为起点写入的，**顺带盖掉了 ota_0 的 app 头** |
| `0x60000` | 非 0xFF，是同一份 app 的后续内容 | 与上一条互相印证 |

## 3. 机制

`hardware/sets/xiaozhi-esp32/partitions/v2/4m.csv` 里，app 分区叫 `factory`，地址就是
**`0x10000`**；而 `v2/16m.csv` 里 app 分区是 `ota_0 @ 0x20000`。

一份**按 4MB 布局编译**的固件被写到了 `0x10000`（对它自己而言地址是对的），但这块板子里的
分区表是 **16MB 布局**。于是：

1. bootloader 按分区表去 `ota_0 = 0x20000` 找 app；
2. 那里首字节是 `0x67`，不是镜像魔数 `0xE9` → 镜像校验失败；
3. `bootloader_utility.c` 的 `bootloader_reset()` 调 `esp_rom_software_reset_system()`
   自杀重启 → `rst:0x3 (RTC_SW_SYS_RST)` → 循环；
4. `CONFIG_BOOTLOADER_LOG_LEVEL_NONE=y` 时 bootloader 一句话都不打，观感就是
   **「屏幕不亮 + 什么也没发生」**。

同类触发点（供以后对照 `bootloader_utility.c` 行号）：无 boot 分区（587）、
无 bootable app（626）、`boot_select == INVALID_INDEX`（`bootloader_start.c:55`）。

## 4. 处置

```bat
:: 1) 先只读体检，确认设备里到底是什么（不写盘）
python hardware/sets/diag.py --board yh-154tft-wifi

:: 2) 整片擦除后全量重烧（清掉外来的分区表/固件残骸）
python hardware/sets/flash.py --port COM18 --clean

:: 3) flash.py 会自动回读逐字节校验，并复位读串口回报「已正常启动 / 在循环重启」
```

## 5. 本次为防复发加的闸（`hardware/sets/flash.py`，默认开启）

1. **烧录前** `check_layout_consistency()`：把 `build/flash_args` 里的每个写入地址
   与**正在写入的那张分区表**对照 —— 除固定的 `0x0`（bootloader）与 `0x8000`（分区表），
   每个地址必须落在某个分区起址上，且 app 必须落在 app 分区。不同源**直接拒烧**：

   ```
   [自检] 烧录地址与分区表对不上
           · xiaozhi.bin 要写到 0x10000，但分区表里没有任何分区起始于该地址
           · app 要写到 0x10000，而分区表里的 app 分区在 0x20000、0x410000 —— 布局不同源
   ```

2. **烧录后** `verify_written_regions()`：回读刚写入的区域逐字节比对
   （>0x20000 的镜像只回读头部 4KB，esptool 本身对写入数据做了全片哈希校验），
   报出首个不同的偏移。
3. **烧录后** `boot_check()`：复位并读 8 秒串口，判 `已启动 / 在循环重启`。
   判据是 **ROM 的 `ESP-ROM:` 横幅不受 sdkconfig 影响** —— 窗口内出现 ≥2 次即循环；
   读到 `I (123) Tag:` 这类应用日志即已启动。
4. 新增开关：`--clean`（先 `erase-flash`）、`--no-verify`、`--boot-check SEC`。
