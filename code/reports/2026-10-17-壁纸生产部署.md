## 二、部署中修复的 bug（commit b4c983ea）

`WALLPAPER_VERSION` 原为写死常量 `"3"`，而固件 WallpaperManager 以 **version 相等作幂等判据**——第二张不同壁纸会因 version 未变被设备跳过下载、永远不生效。已改为按壁纸 md5 派生（`3-<md5>`）：同图重复下发幂等跳过，换图必下载。修复后重打包重部署，实测 `ai_device_config.wallpaper.version = 3-bf22d39e…`。

## 三、端到端冒烟验证（全部通过）

1. **鉴权**：`/wallpaperMag/*` 无 token → `{code:401 未授权}`；`/api/wallpaper/dispatch` 无 Bearer → HTTP 401。生产 Python `auth_key` 与 DB `server.secret` 逐字相等，Java→Python 免配置直通。
2. **上传转码**：240×240 PNG → cover 居中 → RGB565 小端 115200 字节，内容寻址 md5 入库 + 240×240 PNG 缩略图。
3. **匿名下载**：`/wallpaperMag/download/<md5>.bin`（115200 字节，md5 复核一致）与 `.png` 均可匿名下载。
4. **下发**：`dispatch(targetType=devices)` 建任务 → Java 调 Python（`即时下发已受理 devices=1`）→ 设备不在线落 `pending`（文案：设备非直连在线…直连在线后生效）。
5. **device_config 注入**：JSON_MERGE_PATCH 保留 `volume/wake_word/brightness`，新增 `wallpaper{version,url,md5,size,width,height,format}`。
6. **Redis 回执**：`save_ack` 写 → `wallpaper:ack:<id>` → 读回 JSON（ts 毫秒、TTL 7 天）→ 删除，链路通过。
7. **健康**：Python 重启后无壁纸相关报错（日志中仅公网扫描器畸形 HTTP 噪音）；OTA 端点缺 Device-Id 头按预期报错，设备面路由正常。

## 四、契约备注（排查用）

- `dispatch` 的 `targetType` 合法值：**devices / group / all**（复数！`device` 会被拒绝）。
- 错误码 10003（获取参数失败）是多义码：参数缺失、目标设备不存在、目标列表为空都会报它，排查先看 `normalizeTargetType` 与设备 MAC 是否在 `ai_device`。

## 六、二次加固（同日 14:20–14:40，解决「设备在线但任务一直 pending」）

### 6.1 定位到两个真因

| # | 现象 | 真因 |
|---|------|------|
| A | 设备 TCP 12399 心跳常连、控制台却显示 pending | 壁纸只走 WS 8000 直投；固件 WS 是**按次会话**（对话结束即断），空闲态根本没有 WS 连接，必然落 offline |
| B | 就算出现回执也永远读不到，任务不会变 applied | **`config["redis"]` 恒为 None**。生产 `data/.config.yaml` 配了 `manager-api.url`，配置整份走 `get_config_from_api_async()` 从 Java 拉，本地 `config.yaml` 的 `redis` 段被丢弃 → `save_ack` 全程只打日志、不写 Redis |

B 是隐性硬伤：日志里只有一句 `未配置 config.redis（host/url），壁纸回执仅记录日志`，极易漏看。

### 6.2 改动

**投递三级化**（`core/services/wallpaper_service.py` 重写）
1. WS 在线 → 直投；
2. 无 WS 但心跳在线且设备 ADVERTISEMENT 声明 `SET_WALLPAPER` → 走心跳 TCP 通道；
3. 都不可用 → 入**待补投队列**（`wallpaper:pending:<归一化MAC>`，TTL 7 天，Redis 持久化）。

队列语义改为 **last-write-wins：每设备只保留最新一条**（壁纸下发幂等），避免连点多次下发后设备一次上线被灌多条指令、重复下载。

**补投三触发点**：WS hello 注册 / 心跳重连或能力变更（`heartbeat_server.on_device_online`，新增）/ 后台巡检 30s（`start_sweeper`，启动时 `hydrate()` 从 Redis 恢复）。

**配置装配修复**（`config/config_loader.py`）：API 分支后从本地 `config.yaml` 透传基础设施键（`redis`），并在日志中不再静默。

**可观测**：新增 `GET /api/wallpaper/queue`（Bearer = `sys_params.server.secret`，`?flush=1` 立即补投一轮）；Java 侧 queued 文案改为「已排队；设备上线后自动补投，每次下发只保留最新一张」。

### 6.3 实测（生产）

- 队列：同版本重复下发不重复入队；新版本覆盖旧版本；MAC 三种写法归一为同一 key。
- 持久化：`redis-cli ttl wallpaper:pending:44bd8d7b3ae4` = 604800；重启服务后日志 `壁纸队列已从 Redis 恢复 1 条待补投指令`，队列内容一致。
- 巡检：`壁纸巡检: 待补投=1 本轮成功=0 剩余=1`（当前固件未声明 `SET_WALLPAPER`，属预期）。
- 全链路：`POST /yuhe/wallpaperMag/dispatch`（`targetType=devices`、`deviceIds=[...]`）→ 任务 pending + 排队文案 → Redis 队列同步为 `3-<md5>`。
- 本地 10 项单测（去重/覆盖/巡检/WS 补投/未绑定/重启恢复/超期清理）全绿。

### 6.4 仍需固件配合

当前设备跑 2.5.1、`operations=[]`，**心跳通道走不通**。两条可用路径：

1. **不烧录**：跟设备说一句话（建立 WS）→ 队列立即补投生效；或断电重启走 `device_config` 保底。
2. **烧录新固件**（`sets` 四版型已含 `SET_WALLPAPER`）：控制台下发后经心跳通道秒级生效，无需等对话。
