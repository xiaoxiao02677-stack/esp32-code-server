## 3. 服务端即时下发契约（Java ↔ Python，两 agent 并行开发的接口约定）

- Java `POST http://<python>/api/wallpaper/dispatch`，body：`{"device_ids":[...],"wallpaper":{"version","url","md5","size","format"}}`；Python 对在线设备发 WS `{"type":"wallpaper","action":"set",...}`，返回 `{sent:[],offline:[]}`。Java 失败仅记日志（device_config 落库已保底，设备启动/重连时会拉 /ota/config/download）。
- 设备回执 `{"type":"wallpaper","action":"result","version","status":"ok"|"fail","reason"}` → Python 写 Redis `wallpaper:ack:{device_id}`（TTL 7d）→ Java 任务详情读取汇总。
- 老固件兼容（NFR-9）：未知 type 由固件忽略；服务端不过滤、不发不该发的（device_config 注入按设备绑定走）。

### 6.2 关键裁定与偏差

1. **emote 条件编译**：最终落地方案 = display.h 维持上游条件块 + `wallpaper_manager.cc` 的 `WALLPAPER_HAS_LVGL_DISPLAY` 条件闸（emote 板放弃壁纸、屏幕保持默认）。过程中经历 ①→②→① 的往返，以磁盘代码与静态核验为准。**残留**：未实机编译 esp-vocat / esp-sensairshuttle，建议用户构建矩阵各跑一次。
2. **D2 终裁 A**：保 WRAP+72（D1 不乱码为必修项）；LONG_DOT+定高方案被 LVGL 源码证据否决（label 无垂直居中，短句会上移 ~10px 违反 AC-03）；方案 D（`lv_text_get_size` 像素测量裁剪）已论证可行，列为真机验收后备选。
3. **协议回执**：`SendJsonText` 公开薄封装（SendText 保持 protected）；回执字段 `{"type":"wallpaper","action":"result","version","status":"ok|fail","reason"?}`，统一走 `Application::SendWallpaperAck` 单点。
4. **WebP**：JDK 无内置解码器，上传 WebP 返回 10403 提示改 PNG/JPG（装 ImageIO WebP 插件后自动可用）。
5. **回执汇总降级**：xiaozhi-server 未配 `config.redis` 时回执仅打日志（`grep "壁纸回执:"` 可验协议通），Java 任务明细停留 sent/pending 属预期降级；requirements.txt 已补 `redis>=5.0`。
6. **行为简化**：apply 不延后到 idle（下载异步+apply 毫秒级，满足 5s 指标）；开机恢复按 NVS 版本先行、device_config 到达后覆盖。

### 6.3 部署注意（联调前检查单）

- Python：装 `redis` 依赖 + `config.yaml` 加 `redis:` 段（与 manager-api 同实例）；单模块形态需对齐 `server.auth_key` = manager `server.secret`（智控台形态自动等值）。
- Java：Liquibase 自动建三表；`server.ota` 走 8002 的 `/xiaozhi/` 前缀时壁纸下载 URL 无需新增 nginx 规则（`/wallpaperMag/download/**` 已 anon）。
- OTA（Q7）：ai_ota.type 必须与新版型 type 逐字匹配（`yh-154tft-wifi` 等 8 个），老 zhengchen 设备用老 type 的 OTA 行。
- 固件：首次编译前删 `<FW>/build`；实机验收清单见 fw-wallpaper 报告（AC-22~27 对应 5 段日志 `wallpaper: download/verify/apply`）。
