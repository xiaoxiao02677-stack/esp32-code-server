# 2026-10-17　烧 assets 断链 / 刷完不生效　定案

设备：COM18，USB-SERIAL CH340K，ESP32-S3，16MB，MAC `44:bd:8d:7b:41:40`（yh-154tft-wifi）

## 1. 现象

```
Writing 'generated_assets.bin' at 0x00800000...
Flash will be erased from 0x00800000 to 0x00bddfff...
Compressed 4054876 bytes to 2938793...
Writing at 0x00981b87 [========>          ]  32.3% 950272/2938793 bytes...
Hard resetting via RTS pin...
A fatal error occurred: No more data to read from the serial port.
[错误] 烧录失败（esptool 返回码 2）
```

脚本当时把它报成"连不上芯片 / 串口没有数据"，方向是错的。

## 2. 证据：设备里到底有什么（`diag.py` 回读，逐字节）

| 区域 | 地址 | 结论 |
|---|---|---|
| `bootloader.bin` | `0x0` | **[一致]** 15536 字节，与本地 `build/` 完全相同 |
| `partition-table.bin` | `0x8000` | **[一致]** 3072 字节 |
| `ota_data_initial.bin` | `0xd000` | `ota_seq=1` → 已选中 ota_0，**设备启动过**（正常状态） |
| `yuhe.bin` | `0x20000` | **[另一份构建]** 设备 `2.5.1 / Oct 16 21:22:22`，本地 `2.5.1 / Oct 16 23:04:56` |

app 段的差异只有 50/8192 字节，集中在：

- `+0x4`　entry_addr：设备 `0x403799b8`，本地 `0x403799c0`
- `+0x1c`　checksum
- `+0x71`　编译时间串：设备 `1:22:22`，本地 `3:04:56`
- `+0xb0`　segment 内容（地址随入口变化）

**结论：不是写坏，是两批编译。** 而"这次 23:04 的构建没写进 app 段"才是关键。

## 3. 根因（两条）

### 3.1 `--after` 默认 `hard-reset` 在反相板上语义是反的

本板 EN/GPIO0 反相接线：**DTR→EN、RTS→GPIO0**。esptool 的 `hard_reset()` 按
Espressif 参考设计（DTR→GPIO0、RTS→EN）发时序，实际拉到的是 **GPIO0**，芯片不是
被复位而是被拉进/留在下载模式，收尾阶段等不到响应 → `No more data to read`。
这条错误信息此前被脚本理解成"连不上芯片"，把排查带偏。

### 3.2 烧录顺序把 3.9MB 的 assets 排在 app 前面（真凶）

旧流程按 `build/flash_args` 的书写顺序写：

```
0x0      bootloader.bin
0x8000   partition-table.bin
0xd000   ota_data_initial.bin
0x800000 generated_assets.bin     ← 3.9MB，最容易断
0x20000  yuhe.bin              ← 排在它后面
```

assets 一断，**app 一个字节也没写**，设备留着上一次（21:22）的 app。表现就是
"烧过了但没生效"，且 `diag.py` 只报"app 与本地不一致"，很容易误判成写坏。

## 4. 修复（`hardware/sets/flash.py`）

1. **逐段写入（默认）**：一个镜像一个 esptool 会话，某段断了只重写那一段。
2. **按地址升序**：`bootloader → 分区表 → otadata → app → assets`，assets 垫底。
   它断了设备照样能启动，缺的只是字库 / 表情 / 唤醒词。
3. **自动降速重试**：段内 `460800 → 230400 → 115200`。
4. `--after` 默认改 `auto`：反相板 `no-reset`（写完由脚本按正确时序复位），
   标准板 `hard-reset`。
5. 失败诊断按"哪一段坏的"分叉：首段失败才是连接问题，中途失败明确说
   "写到一半断链"，并给出降速 / `--skip-assets` 的具体命令。
6. 新增 `--single`（退回一次性写全部）、`--skip-assets`。
7. `ota_data_initial.bin` 不再参与逐字节比对 —— 设备启动一次后 bootloader 会把
   `ota_seq=1` 写进去，逐字节比必然误报；改为播报状态。

## 5. 修复（`hardware/sets/diag.py`）

新增 `describe_app()`：解析 `esp_app_desc`（magic `0xABCD5432`）比对版本 / 日期 /
时间，把"逐字节不同"细分成 `[不一致]`（写坏）和 `[另一份构建]`（另一批编译）。
`otadata` 同样改为状态播报。

## 6. 处置

```bat
:: 分段写、assets 垫底、自动降速
python hardware/sets/flash.py --port COM18 --baud 230400

:: 复核（只读，跑完把设备复位回运行态）
python hardware/sets/diag.py --port COM18
```

预期：`diag.py` 五段全部 `[一致]`，`otadata` 显示 `[信息]`，`[启动检查]` 读到
应用日志。

若 assets 反复断：`--baud 115200`；仍不行先 `--skip-assets` 确认应用能起来，
再单独补 assets。连续同一位置断更可能是供电（写 4MB 时电流冲击最大）——
换 USB 口 / 拔外设 / 带供电 HUB / 先调暗背光。

## 7. 待确认

设备当前（未重烧）已经是"能启动"状态：bootloader / 分区表是 23:04 的，app 是
21:22 的同版型构建，`otadata` 指向 ota_0。屏幕若已正常点亮，说明只剩 assets
需要补齐；若仍不亮，则问题不在烧录链路，应打开

# 第二轮加固（11:27 起，目标：不再出现「连接失败 / 烧录失败」）

用户确认设备已能正常启动。这一轮把两条失败路径都从"靠运气"改成"靠机制"。

## 8. 失败路径二分：连接 vs 传输

以前两者共用一条错误文案，实测中"写一半断链"被误报成"连不上芯片"，排查方向全偏。
现在分开处理：

| 失败点 | 机制 |
|---|---|
| **连接** | 每段写之前先跑 `esptool flash-id` **探活**（实测 1.8 秒）。失败重试 `--attempts`（默认 3）次 → 降一档波特率再来 → 还不行就**换另一条复位线序**（自动识别偶尔认错；认对的那条会写回 `plan.order` 沿用到后面所有段） |
| **传输** | 大镜像按 **1MB 切块**（app 3 块、assets 4 块），崩一次只重写这 1MB。块边界与 4KB sector 对齐，相邻块擦除不会互相吃尾巴 |

最坏组合：`3 次探活 × 2 种线序 × 2~3 档波特率`，全用完才报错；报错时明确区分
"连接阶段没上去"与"传输中途断了"，并给对应命令。

## 9. 默认参数调整

| 项 | 旧 | 新 | 理由 |
|---|---|---|---|
| `--baud` | 460800 | **230400** | 460800 在长线/劣质线材 + 4MB 镜像时实测断链；慢一倍换"不返工" |
| `--attempts` | 2（只在一次性模式生效） | **3（每段探活次数）** | 分段模式下也真正生效了 |
| 大镜像切块 | 无 | **1MB，超 1.5MB 才切** | 见上 |

新增 `--chunk-size BYTES`（支持 `512K` / `1M`）、`--no-chunk`。

## 10. 校验从"只看头"改成"头 + 尾"

`verify_written_regions()` 现在：

- 小镜像（≤128KB）：全量回读比对；
- 大镜像：读 **头部 4KB** + **尾部 4KB**。
  - 头部能发现"写到了别处 / 写错文件"；
  - 尾部能发现"写到一半断链"—— app 镜像末尾就是整段镜像的 SHA256，
    最后 4KB 对得上基本等于整段写完了。

实测区间：`yuhe.bin` 尾 @ `0x2c0330`（文件内 `+0x2a0330`），
`generated_assets.bin` 尾 @ `0xbdcf59`（文件内 `+0x3dcf59`）。

## 11. 验证

| 项 | 结果 |
|---|---|
| `probe_connection` 实测（COM18，反相板） | 230400 / 460800 / 230400 三次全部成功，每次 1.7~1.9 秒 |
| `slice_chunk` 切分（yuhe.bin 2.75MB → 3 块） | 每块与原文件对应区间逐字节一致；拼回整体一致 |
| 校验区间规划 | 3 个小镜像全量 + app/assets 各头尾两段 |
| 语法 / `--help` | 通过 |

端到端真实烧录按惯例由用户执行：

```bat
python hardware/sets/flash.py --port COM18 -y
python hardware/sets/diag.py --port COM18
```

## 12. 补掉 diag 的盲区：它之前根本不查 assets

`diag.py` 原本只查 bootloader / 分区表 / otadata / app，**不查 assets** —— 而两次
翻车都坏在这块。现在补上 `0x800000` 的**头 4KB + 尾 4KB** 比对。

补完一查就抓到实情：

```
generated_assets.bin   0x800000  [一致]  头部：一致（4096 字节）
generated_assets.bin   0xbdcf59  [空白]  尾部：设备上是空白（全 0xFF，4096 字节）
```

顺着往前扫 192KB：**设备上最后一个非 0xFF 字节在 `0xBADF58`**，本地 assets 末尾
应在 `0xBDDF59` —— 即 assets 只写到约 **95%**，尾部 **192KB 全是 0xFF**。

这与用户"能正常启动了"并不矛盾：assets 排在 app 之后，它断了不影响启动，缺的
是末尾部分表情 / 字库资源。**说明那轮 assets 仍然断链，只是断在 95% 而不是 32%。**

## 13. 新增 `--only`：只补坏掉的那一段

```bat
python hardware/sets/flash.py --port COM18 --only assets -y   :: 只补 3.9MB 资源分区
```

可用名：`bootloader` / `partition-table` / `otadata` / `app` / `assets`，可逗号组合。

实现上 `--only` 是在**自检之后**过滤的：布局核对始终针对完整清单，所以
`--only assets` 不会因为"计划里没有 app 镜像"被拒烧。
