# 2026-10-15（晚）push-scheduler 推送音频设备端播放失败修复

## 需求
- 现象：`https://sandyun.top:8001/#/admin/push-scheduler` 推送后硬件未完整播放；设备日志：收 SEND_NOTIFY(url=…mp3) → 300ms 后 `NotifyPlayer: Notification Ogg stream ended before a complete audio stream` → playback 1 failed
- 要求：模拟硬件通信链路彻底排查；多 agent 协同（两轮共 21 个子 agent 全部因基础设施 406/503 失败，**全部工作由主 agent 亲自完成并已告知用户**）

## 双根因
- **根因 B（决定性）格式不匹配**：固件 NotifyPlayer 只拉 `audio/ogg` 并喂 OggDemuxer——**只支持 Ogg Opus 单声道**（首包 OpusHead 声道=1、次包 OpusTags、帧时长 SILK 10/20/40/60ms、CELT 2.5/5/10/20ms、混合 10/20ms、采样率 8-48k）；服务端 doubao_v3 TTS 落盘 MP3 → **任何 MP3 URL 必然 300ms 失败**
- **根因 A（次要）火山上游垃圾**：doubao_v3 流式合成每个 MP3 在 LAME3.100 结束标记后附加 150-450B 的 0xAA/0x55；复现 6/6；ffmpeg 解码 0 错误时长完整（垃圾在有效流后被播放器忽略——长期掩盖因素）
- `dec=44 out=42` 是 AudioService 30s 周期累计计数（开机提示音），与推送无关；用户听到的"部分播放"即开机音
- `sent=1` 只代表送达 WS 通道；yh_protocol.cc L416-437 先 ACK 再异步 Schedule 播放 → 服务端 sent ≠ 设备播放成功

## 修复（已部署生产）
- `core/services/topic_generator.py`（生产 /root/xiaozhi-server/main/xiaozhi-server/）：`_synthesize_tts` 落盘后调新增 `_ensure_device_playable_audio`——二进制探测(OggS+OpusHead)通过原样返回；否则 ffprobe 校验时长(<0.5s 抛错) → `ffmpeg -ac 1 -ar 24000 -c:a libopus -b:a 32k` 转 .ogg → `os.replace`+删 MP3；ffmpeg 缺失降级保留+WARNING
- 注意 ffmpeg 临时输出必须带 `.ogg` 扩展名（无扩展名 rc=234 Unable to choose output format）
- 部署后重启 xiaozhi-server.service，端到端验证：真实推送产物 `topic-1792058396395-14c19fd13348.ogg`(5959B)，模拟器判线上 URL **PLAYABLE（4页/75包/1500ms/24kHz mono）**
- 备份：`topic_generator.py.bak-20261015T095759Z`；补丁/原版/回滚见 `code/fixes/push-audio/`
