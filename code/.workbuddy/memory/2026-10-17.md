## 烧 assets 断链 → 定位「app 段根本没写」+ flash.py 改逐段烧录（11:14 起）

**现象**：`Writing 'generated_assets.bin' at 0x00800000` 到 32.3% 后
`Hard resetting via RTS pin` + `No more data to read from the serial port`，
esptool 返回码 2；旧脚本一律报"连不上芯片"，方向带偏。

**设备取证（diag.py 回读 COM18 / ESP32-S3 / 16MB / MAC 44:bd:8d:7b:41:40）**：
- `0x0` bootloader **[一致]**、`0x8000` 分区表 **[一致]**、`0xd000` otadata `ota_seq=1`
- `0x20000` app **[另一份构建]**：设备 `2.5.1 Oct 16 21:22:22`，本地 `2.5.1 23:04:56`
- 差异 50/8192 字节，落在 `+0x4` entry(0x403799b8 vs …c0) / `+0x1c` checksum / `+0x71` 编译时间串

**根因两条**：
1. **顺序**（真凶）：旧流程照 `build/flash_args` 书写顺序写，3.9MB 的 assets 排在
   app **前面** → assets 一断，app 一个字节没写，设备留着上一次 21:22 的 app。
   表现为"烧过了没生效"，且 diag 只报"不一致"，极易误判成写坏。
2. **`--after hard-reset` 在反相板上语义反了**：DTR→EN / RTS→GPIO0，`hard_reset()`
   拉到的是 GPIO0，芯片留在下载模式 → 收尾读不到响应 → `No more data`。

**flash.py 改动**：
- 默认**逐段写入**（一镜像一 esptool 会话），顺序**按地址升序**：bootloader → 分区表 →
  otadata → app → **assets 垫底**（它断了设备照样能起，缺字库/表情/唤醒词）
- 段内自动降速 `460800 → 230400 → 115200` 重试
- `--after` 默认 `auto`（反相板 `no-reset`，由脚本自己按正确时序复位）
- 失败诊断按"首段/中途"分叉，不再把"写一半断链"说成"连不上芯片"
- 新增 `--single`（退回一次性）、`--skip-assets`
- `ota_data_initial.bin` 不参与逐字节比对（设备启动一次 bootloader 就写 `ota_seq=1`，
  逐字节比必然误报），改播报状态 `describe_otadata()`

**diag.py 改动**：新增 `describe_app()`（解析 `esp_app_desc` magic `0xABCD5432` 比对
版本/日期/时间），把"逐字节不同"分成 `[不一致]`（写坏）与 `[另一份构建]`（另一批
编译）；otadata 同样改状态播报。

**报告**：`code/reports/2026-10-17-assets断链定案.md`

**当前设备状态（未重烧）**：bootloader/分区表是 23:04 的、app 是 21:22 同版型、
otadata 指向 ota_0 → 已经是"能启动"的组合，只差 assets 完整。

## flash.py 二轮加固（11:27，用户要求"别再出现 flash/连接失败"）

设备已确认能正常启动。这轮把失败路径改成机制化：
- **连接 vs 传输二分**：每段写之前先 `esptool flash-id` 探活（实测 1.8s/次）；
  失败重试 3 次 → 降档 → **换复位线序**（认对的那条写回 `plan.order` 沿用）
- **大镜像 1MB 切块**（>1.5MB 才切；app 3 块、assets 4 块），崩一次只重写 1MB；
  块边界与 4KB sector 对齐，相邻块擦除不互吃
- **默认 `--baud` 460800 → 230400**（实测 460800 写 4MB 会断，慢一倍换不返工）
- `--attempts` 默认 3，语义改为"每段探活次数"，分段模式真正生效
- 新增 `--chunk-size`（支持 `512K`/`1M`）、`--no-chunk`
- **校验改头+尾双端**：大镜像读头 4KB + 尾 4KB（app 末尾是整段 SHA256，
  能发现"写一半断链"）；实测尾部区间 app @0x2c0330、assets @0xbdcf59
- 失败文案分叉：首段失败=连接问题（给换线/占用/手动进下载模式步骤）；
  中途失败=传输断链（给降速/切细/供电建议）

**验证**：探活 3 次全成功（1.7~1.9s）；`slice_chunk` 切 2.75MB 成 3 块拼回逐字节一致；
语法与 --help 通过。端到端真实烧录仍由用户手动执行。

## diag 补 assets 盲区 → 抓到实情：assets 只写到 95%

`diag.py` 原本不查 assets（两次翻车都在这），补上 `0x800000` 头 4KB + 尾 4KB 比对后立刻抓到：
- 头部 `[一致]`、尾部 `[空白]`（全 0xFF）
- 顺扫：**最后一个非 0xFF 字节在 0xBADF58**，本地末尾应在 0xBDDF59 → **尾 192KB 没写**
- 即那轮 assets 断在 ~95%，但排在 app 后面 → 设备照常启动，缺的是末尾部分表情/字库

**新增 `--only NAME`**（bootloader/partition-table/otadata/app/assets，可逗号组合）：
`--only assets` 只补资源分区。**过滤发生在自检之后**，否则会因"计划里没有 app"被拒烧。
