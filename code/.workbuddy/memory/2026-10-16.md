## 摄像头板第三轮（20 agent）：黑屏 + 摄像头 0x106 根因定位与修复
- **找到上游 pristine 副本**：`G:/demo/21_xiaozhi/hardware/camera/main/boards/lckfb/szpi-esp32s3/`（lckfb_esp32s3_v1.0 官方例程，`git show HEAD` 校验与本工程字节一致）。板照 `hardware/camera/docs/v1/lichuang-s3.jpg`。**这是本板最高价值基准，以后改板先 diff 它。**
- **PCA9557 各 bit 权威定义（立创官方 wiki，推翻此前所有猜测）**：
  - **IO0 = LCD_CS（低电平选通）** ← 不是 RESET！
  - IO1 = PA_EN（功放）
  - **IO2 = DVP_PWDN（高电平掉电 / 低电平使能）** ← 不是"高有效供电使能"！
  - IO3~7 保留未用（故 `in=0xF7` 的 bit3=0 无意义）；0x02 Polarity Inversion 上电默认 **0xF0**（bit4~7 读回反相，bit0~3 不反相）
- **黑屏根因**：上一轮按《TFT 原理图》把 bit0 当"低电平复位"→ 稳态停在 **1** = 永久取消片选（或永久复位），之后所有 SPI 命令屏幕一概不收 → 全黑。**稳态必须是 0**。佐证：① 本工程 `docs/lckfb-szpi-摄像头板适配说明.md:74/:158` 早记载「bit0 高有效复位，曾误加 init 后置 1 → 黑屏，已回退」——本轮又踩回去；② 横向 zhengchen/cam:205、zhengchen/cam-ml307:209、rymcu/bigsmart:146 全部 `SetOutputState(0,0)` 且全程保持 0；③ pristine 也是 0。本板曾是全仓库唯一停在 1 的板。

- **本轮改动**（`lichuang_dev_board.cc` 724 行 + `config.h`）：
  - `DISPLAY_BACKLIGHT_OUTPUT_INVERT` 回退 **true**（pristine config.h:39 + 板信息 md:60「低电平有效」双佐证；Q2 栅极 R21 上拉 3V3 说明是 P-MOS，低电平导通）

## 第 14 轮（08:30）：UDP 通道 hostname 被截出 `wsandyun.top` —— `erase` 参数写错

**现象**：设备 WebSocket 正常连通，但 UDP 心跳通道失败：
```
E (11962) EspUdp: Failed to get host by name
E (11962) WS: Failed to connect UDP to wsandyun.top:8002: DNS resolution failed (dns_failed, native=210)
```
同时有一条无害警告：`Server sample rate 16000 does not match device output sample rate 24000, resampling may cause distortion`

**根因（一行代码）**：`main/protocols/websocket_protocol.cc:347`
```cpp
auto scheme_pos = host.find("://");
host.erase(scheme_pos, 3 + 1);   // ❌ 错：erase(index, count)
```
`std::string::erase(pos, count)` 第二参是**删除个数**，不是结束下标。
对 `ws://sandyun.top:8002/xiaozhi/v1/`：`find("://")=2`，`erase(2,4)` 删掉 `: / / s` 四个字符
→ `ws` + `andyun.top` = **`wsandyun.top`**（正是报错里的域名）。`wss://` 同样错（变 `wss<host>`）。

**修复**：`host.erase(0, scheme_pos + 3);` —— 删到 `://` 之后（ws→erase(0,5)、wss→erase(0,6)，两者皆正确）。
同文件后续 `find(':')` / `find('/')` 的 erase(single-arg) 用法是对的（erase(pos) 到结尾），不用动。

**★ 通用教训**：`std::string::erase` 有 `erase(pos,len)` 与 `erase(first,last)` 两个重载，
**两参数版本极易误当成 `(start,end)`**。做 URL/scheme 剥离务必写 `erase(0, pos+n)`，
或直接用 `substr(pos+3)`。全仓库仅此一处该模式（已 grep `erase(scheme_pos|find("://")` 确认唯一）。

**采样率那条 W 不用处理**：服务端 hello 的 `audio_params.sample_rate=16000` 与设备 codec 输出 24000 不一致，
固件自动重采样，属信息级提示，不影响 UDP/WS 链路。若要消掉需让两边一致（改服务端 TTS/ASR 配置为 24000，
或把设备输出降到 16000），否则接受轻微重采样失真。

**编译命令（用户手动执行）**：`build_zhengchen_cam.bat`（内部即 `python scripts\build.py zhengchen/cam`）

## 第 16 轮（09:10）：TTS 播到一半被"滴~"打断 —— 设备自己的声音触发人声打断（已修复）

```
I (35712) Application: Abort speaking   ← 只播了 470ms
I (35712) Protocol: Send abort speaking (reason=0)
I (35712) StateMachine: State: speaking -> listening
I (35712) Protocol: Send start listening (mode=2)
I (35732) Application: TTS session done (sentences=1, duration=2719 ms)
I (36302) Application: Playback drained
```

**★ 取证要点（以后判断打断来源就看这两条）**
- `reason=0` = `kAbortReasonNone` → **不是唤醒词打断**（唤醒词是 `reason=wake_word_detected`），
  而是 `application.cc` 主循环 `MAIN_EVENT_VAD_CHANGE` 的 speaking 分支（"人声打断"）。
- 紧跟 `Send start listening (mode=2)` + `Playback drained` → 精确匹配该分支的
  `AbortSpeaking → 清队列 → SetDeviceState(listening) → SendStartListening → ResetDecoder → PlaySound(OGG_POPUP)`。
  **用户听到的"滴~"就是最后那句 `PlaySound(Lang::Sounds::OGG_POPUP)`**（打断提示音，是结果不是原因）。

**根因链**
1. `sdkconfig: CONFIG_USE_DEVICE_AEC=y` → `aec_mode_=kAecOnDeviceSide`
   → `GetDefaultListeningMode()` 返回 **`kListeningModeRealtime`（mode=2，日志里就是这个 2）**。
2. Realtime 模式下 `HandleStateChangedEvent` 的 speaking 分支**刻意不关闭语音处理**
   （`listening_mode_ != kListeningModeRealtime` 才关），目的就是支持边播边听、随时打断。
3. 但 AEC（`AEC_MODE_FD_LOW_COST`）在 TTS 刚开始播放的几百 ms 内**还没收敛**，codec 起停也有瞬态，
   设备自己喇叭的声音漏回麦克风 → AFE 的 VAD（`vad_mode=VAD_MODE_0` 最灵敏、`vad_min_noise_ms=100`）
   判成 `VAD_SPEECH` → 立刻回调 `on_vad_change(true)` → 打断自己。

**修复（4 个文件 6 处，三道防线）**
1. `audio/engines/afe_audio_engine.{h,cc}`：**VAD 去抖**。
   新增 `vad_candidate_/vad_candidate_since_us_/kVadSpeechConfirmMs=200/kVadSilenceConfirmMs=300`，
   `HandleVoiceResult` 改为 `UpdateVadState(result->vad_state == VAD_SPEECH)`：
   候选状态需**连续保持** 200ms(人声)/300ms(静音) 才翻转并上报，滤掉几帧的回声尖峰。
   `EnableVoiceProcessing(bool)` 两端都调 `ResetVadState()`。
2. `audio/audio_service.{h,cc}`：**新增 `GetPlaybackElapsedMs()`**。

   `MarkPlaybackDrainedLocked()` 排空时清零。
3. `application.cc`：**播放起始保护窗** `kSpeakingInterruptGuardMs = 600`。
   VAD_CHANGE 的 speaking 分支先取 `GetPlaybackElapsedMs()`，< 600ms（或 -1）就打印
   `Ignore voice interrupt in playback guard window (%d ms)` 并**忽略打断**；≥ 600ms 才走原打断逻辑
   （并新增 `Voice interrupt after %d ms of playback` 便于对照）。
4. `application.cc` + `audio_engine.h`：**AEC 不生效就关闭边播边听**。

## ★ 烧录报 `Invalid head of packet (0x49)` —— 根因：板子复位线序是反相的

用户实测 `esptool ... --before default-reset write-flash @flash_args` 反复失败：
`A fatal error occurred: Failed to connect to ESP32-S3: Invalid head of packet (0x49):
Possible serial noise or corruption.`，且明确说「我就是按住 BOOT 开机的」。

### 定位过程（全部用实物 COM18 跑出来的证据，不是猜）
1. `--list --identify` 采样里读到 `I (104428) AudioService: Enabling audio testing..`：
   uptime 104 秒 = 复位脉冲**根本没让芯片重启**，采样里也没有 `ESP-ROM:` 横幅。
2. 关键洞察：**0x49 = ASCII `I`** —— 正是应用日志首字节（`I (51458) SystemInfo: ...`）。
   esptool 把日志当成了应答包 → 芯片在跑应用，没进下载模式。
3. 写了四种线序的对照实验（`dtr/rts` 组合 + 发 esptool SYNC 包 `c0 07 07 12 20 + 55*32`）：
   - 复刻 esptool `ClassicReset`（`dtr=F,rts=T` 0.1s → `dtr=T,rts=F`）→
     `boot:0x1b (SPI_FAST_FLASH_BOOT)` = **进了应用**（因此日志污染应答）
   - 镜像时序（`dtr=T,rts=F` 0.1s → `rts=T,dtr=F`）→
     `boot:0x13 (DOWNLOAD(USB/UART0)) ... waiting for download` = **下载模式** ✅
   → 结论：本板 **DTR→EN、RTS→GPIO0**，与 Espressif 参考设计正好相反。
4. 读 esptool 源码核对：`esptool/reset.py` 的 `ClassicReset` 与我复刻的一致；
   `loader.py:441-442` 打开串口**前**就设 `rts=False,dtr=False`（不打扰已进下载模式的芯片）
   → 所以「我们自己复位 + `--before no-reset` 交给 esptool」这条路可行。
5. 接管实测：镜像复位后 `esptool --before no-reset read-mac/flash-id` 在 115200 与 460800
   **都一次连上**：ESP32-S3 (QFN56) rev v0.2 / MAC 44:bd:8d:7b:41:40 / Flash 16MB。

### flash.py 改动（+523/-… 行）
- 新增第 3 节「下载模式」：`ResetPlan` / `detect_reset_order()` / `enter_download_mode()` /
  `resolve_reset_plan()` / `diagnose_after_failure()`；`_reset_lines(order)` 取代原 `_pulse_reset`
- CLI 新增 `--reset {auto,esptool,reversed,none}`（默认 auto）、`--manual`、`--before`、

- `--identify` 判据改为「真的落进下载模式」才算命中线序（原来读到 ROM 横幅就跳出，

## ★ 无限重启定案：板子里是「4MB 布局的 app + 16MB 布局的分区表」（23:40-00:10）

用户反馈刷完 `bootloader_reset at bootloader_utility.c:1163` + `rst:0x3 (RTC_SW_SYS_RST)` 无限循环。
**不是固件问题，是设备里「分区表与 app 不同源」**。取证（COM18，只读）与结论：

设备实况（`hardware/sets/diag.py` + 逐段回读，证据留在 `.trash/dev_dump/`）：

| 区域 | 设备上是什么 | 说明 |
|---|---|---|
| `0x0` bootloader | 入口 `0x403c88f4`、16736 字节 | 与 `hardware/big_secreen/.../build/bootloader/bootloader.bin` **只差 36 字节**，**不是** sets 这次的（`0x403c88dc`/15536） |
| `0x8000` 分区表 | **16MB 布局**（ota_0@0x20000、ota_1@0x410000、assets@0x800000） | 与 `build/partition_table` 逐字节一致；三套工程（sets/big/smallcam）这张表**完全相同**，故它不能反证是谁写的 |
| `0xd000` otadata | `01 00 00 00` 合法 ota_0 记录 | 本地产物是**全 0xFF** → 这条是设备早期运行时自己写的，非本次写入 |
| **`0x10000`** | **一份完整合法 app 镜像**（`e9 06 02 4f`、entry 0x403799c0、6 段、seg0 len 0xa81b8） | `esp_app_desc` = **2.5.3 / Oct 16 2026 22:13:45 / v6.1-dirty**；**全仓找不到任何 2.5.3 产物，git 历史里也从未有过** |
| `0x20000`（ota_0） | **不是镜像头**，首字节 `0x67`=`'g'`，是一段字符串 | 正是 0x10000 那份 app 的**内部 rodata**（偏移 0x10000）——即它被写进来时长 2.7MB，**盖住了 ota_0 的 app 头** |

**机制**：`partitions/v2/4m.csv` 的 `factory` 分区在 **0x10000** —— 一份按 4MB 布局编译的固件
被写到 0x10000（对它自己是对的），而板子里分区表是 16MB 布局（app 应在 0x20000）。
bootloader 去 0x20000 找 ota_0，首字节不是 `0xE9` → `bootloader_utility.c:1163` `bootloader_reset()`
自杀重启 → 无限循环 + 屏幕全程不亮（`BOOTLOADER_LOG_LEVEL_NONE=y` 时它一句话都不打）。

**结论：这一轮 `flash.py`/`build.py` 的产物没问题，是板子里先有了外来布局的固件；
而且目前 0x0/0x20000 都没有我们的内容 —— 上一次烧录（23:04 那次）实际没写进芯片**（很可能是 0x49 连接失败那一轮）。

**本次交付**：
- 新增 `hardware/sets/diag.py`（只读体检：回读 0x0~0x10000 + 0x20000，与 `build/*.bin` 逐字节比对，
  给出首个不同偏移与「烧录问题 / 产物问题」结论）
- `hardware/sets/flash.py` 加三道闸：① 烧录前核对「写入地址 vs 正在写入的分区表」布局同源（不同源直接拒烧）；
  ② 烧录后回读逐字节比对（app 只回头部 4KB，esptool 本身有全片哈希）；③ 复位读串口判定「已启动 / 循环重启」
- 新增 `--clean`（先 `erase-flash` 整片擦除再全量烧）、`--no-verify`、`--boot-check SEC`
- 判循环重启的判据：**ROM 的 `ESP-ROM:` 横幅不受 sdkconfig 影响**，8 秒内出现 ≥2 次 = 在循环
- `hardware/sets/README.md` 同步：三脚本分工表、新参数表、「刷完起不来」两处 FAQ
