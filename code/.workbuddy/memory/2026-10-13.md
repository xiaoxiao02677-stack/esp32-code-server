- **重要机制发现**：xiaozhi-server 的 load_config 在 `.config.yaml` 含 `manager-api.url` 时走 `get_config_from_api_async`——运行时配置整体来自 Java API；本地 server 段仅保留 ip/port/http_port/vision_explain/auth_key 四项，**其他本地 server 键（如 heartbeat_port）会被忽略**。心跳端口要改须改 Java API 返回的配置或代码（`core/heartbeat.py` 读 `server.heartbeat_port`，默认 12399）。
- Java 下发配置由 `sys_params` 表全量构建（param_code 点号分层），缓存在 Redis（RedisKeys.getServerConfigKey()），改 sys_params 后需重启 Java/清缓存才生效。

## ASR→LLM→TTS 链路延迟测试与优化报告完成（05:41-06:10 UTC+8，5 agent）
- 需求：模拟 ASR(文字代替)→LLM→TTS 链路，测各阶段通信时间并给优化方案。禁止改码，只读。
- 5 agent：chain-mapper（链路代码）/ tester-auditor（测试器审计）/ live-prober（远程实测）/ bench-researcher（行业基准）/ perf-writer（成文，通道失效，由 main 整合成文）
- 产出：`.workbuddy/docs/latency_chain_optimization_report.md`
- 实测关键数据（live-prober，SSH sandyun.top:22223 密钥免密，项目 /root/yh/app/xiaozhi-server）：
  - LLM=DeepSeek deepseek-flash 流式：首 token P50 0.58s/P95 0.84s，总耗时 P50 1.09s
  - TTS=qwen3-tts-flash 非流式：0.91~1.62s/句，1 次 30.98s 瞬态长尾（无重试，tts_timeout 15s/相位双段）
  - **EdgeTTS 全部 403 不可用**（微软端点拒绝，本机对照也 403），fallback 链同指向 EdgeTTS 等于无兜底
  - 网络 RTT 正常（deepseek 115-127ms / qwen 91-173ms / bing 236-331ms）
- 核心结论：E2E TTFA ≈1.5-2.2s（合格档上限）；最大瓶颈=非流式 TTS 整句合成
- 优化路线：第一步零代码（换火山 doubao 双向流式 TTS，config.yaml:815-879 已预留 huoshan_double_stream + 修 timeout + 修 fallback）→ TTFA≈1.0s；第二步连接复用+4 处打点→≈0.9s；第三步 memory 并行+段间预合成+首句缓存→≈0.8s 优秀档
- 注意：生产 LLM/TTS 配置经 manager-api 按设备动态下发（静态 config.yaml 仅参考），官方测试器测不到动态配置，需从 MySQL ai_model_config.config_json 取
